# MVP 事实、技术与产品审计

审计日期：2026-07-13  
审计基线：`6fccb39`（`main`）

## 仓库与部署现状

- 工作树在审计开始时干净，`main` 与 `origin/main` 同步。
- 历史由一个初始 MVP 分支的七个线性提交和一次合并组成；没有迁移、测试或数据校订历史。
- 生产面只有 `index.html`、`styles.css`、`data.js`、`app.js` 四个运行文件。
- GitHub Pages workflow 直接上传整个仓库，没有安装、校验、测试或构建步骤。
- 没有包管理器、类型检查、schema、测试、正式许可、内容许可或贡献流程。
- 仓库及其父目录没有适用于本项目的 `AGENTS.md`。

## 当前产品假设

### 保留

- “先区分身份／资望／实际工作，再解释完整官衔”的入口。
- 总览、制度地图、官名、制度沿革、人物官履、原文解码六类任务入口。
- 纸色、墨色、朱砂和玉色组成的克制中文视觉；宋体正文与无衬线界面文字的层次。
- 页面在桌面双栏、移动单栏的总体信息布局。
- 规则驱动而非伪装全知 AI 的解码方向。

### 必须升级

- hash 切换视图升级为真正 URL 路由和实体深链接。
- 静态卡片“地图”升级为有方向、关系类型和有效期的制度关系投影。
- 官履单列表升级为任命动作、任职阶段、官衔成分和多维评估的组合视图。
- 关键词包含匹配升级为可解释的最长匹配、动作词和句法候选解析。
- 视觉 token、焦点样式、跳转链接、键盘交互、reduced motion、打印和图表文本替代系统化。

## 高风险或可能误导的现有表述

以下不是认定其必然错误，而是认定当前仓库没有足够依据把它们作为可引用结论发布：

- 所有机构的职能和关系说明均没有时期版本和具体来源。
- “财政主要由三司系统掌握”“六部职事体系更具现实行政意义”等概括没有断言层，也没有区分制度规定与实际运行。
- 每个官名的 `periods` 是宽泛浏览标签，不足以证明真实有效期。
- `sourceHint` 只写“《宋史·职官志》”或“某制度研究”，不能定位到版本、卷、页、条目或段落。
- 苏轼 1071、1074、1077、1089 等记录只给公历年，不说明纪年原文、换算依据、精度、赴任或离任。
- “龙图阁学士、知杭州”作为 1089 完整官衔没有来源定位，不能直接迁移。
- 1094 节点明确写有“示例节点，完整官衔待录”，必须从生产移除。
- 王安石两条、司马光两条记录明确包含“示例”“待补”“占位”，必须隔离为被拒绝的 demo fixture 或删除。
- 用 `political` 单一短语表达政治位置会遮蔽名义品级、实际权力、中心度、资望和皇帝信任的差异。
- 解码器会对相互覆盖的别名做字符串排除，但不保存匹配范围、观察时期、歧义、未知片段或动作关系。

## 本地 SongScope 可复用原则

已审阅 `/home/qchen/projects/songscope/docs/design-book/` 与 `packages/schema`。可复用：

- 实体／事件／状态／关系／断言／证据／投影分层；
- 不依赖名称的稳定 ID 与可变 slug；
- 原始时间、标准化范围、精度和认知不确定性分开；
- 任命动作、官衔成分和实际任职阶段分开；
- `Source → Edition/Item → Locator → Passage` 与冲突断言；
- 前端投影可重建并携带生成规则版本。

不复用：

- PostgreSQL/PostGIS 作为公共站点运行依赖；
- 通用宋史平台的作品、灾害、社会网络等广域本体；
- SongScope 当前较窄的官职枚举和置信度单分数；
- 其内部 `ss:` ID。除授采用独立 `chs:` ID，并可通过 `ExternalIdentifier` 对齐。

## 审计结论

当前界面是有价值的产品和视觉种子，但当前数据没有一条可因“已经存在”而自动升级为正式史实。迁移应以新的证据中心 schema 为边界：先隔离旧数据，再从可定位来源重录；前端只消费通过校验生成的投影。
